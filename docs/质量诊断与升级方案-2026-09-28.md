## 2. 新的生产单位：一个人、一个问题、一个结果

不再默认从 GitHub 热榜拿三个仓库凑一期。每个候选先写四句话，答不出来就不生产：

1. **谁**会在今天遇到这个问题？用具体身份和场景描述，避免“所有 AI 用户”。
2. **他想完成什么**？用日常语言写任务，不用“智能体外壳、协作件、可见度报告”作问题。
3. **30 秒内能给什么证据**？真实运行、前后对比、录屏、官方演示的明确标注，至少一个。README 文字可以核事实，不算成效演示。
4. **看完能做什么决定**？给出一个可执行动作或清楚的“谁不适合”。“关注我”“先想清楚”不算。

候选准入改为**四项全满足**，再做评分：受众相关性、结果强度、证据可拍性、信息差各 0–3 分，低于 9/12 不做。事实风险仍是独立硬门，不能用高热度抵消。**每个问题最多介绍 1–2 个工具**；三工具清单须证明三者属于同一任务、互相可比，并能逐个展示实际结果。未实测的项目可做“官方公告简报”，不得包装成推荐或教程。

题材试行配比：4 条实用任务/真实演示，2 条避坑或选择对比，最多 1 条需要当天行动的新闻。比例是排期方向，缺少好选题时少发。原则上每个发布窗口只发一条同系列视频；不为了补日更数量连续发布相近清单。

## 3. 脚本和画面：先让观众看见结果

**默认 25–40 秒，按信息量伸缩为 4–6 个画面节拍**，不强制五场、三工具或每场一个完整句。45–60 秒需要有额外的实际步骤或对比证据，不能用许可和免责声明填长。事实口径可在画面以简短来源标注，完整来源留发布文案。

| 时间 | 应发生什么 | 不通过示例 |
|---|---|---|
| 0–2s | 具体结果或问题，画面直接展示结果/失败/对比；第一帧已清晰可读。 | “最高 6839 星”“三个开源件”“AI 更新太快”。 |
| 2–5s | 给第二个理由：真实效果、关键限制或可比较的差别。 | 只亮仓库名、许可证、章节号。 |
| 5–25s | 逐步展示一个任务如何做、做到什么、哪里做不到；画面跟着口播变。 | 抽象箭头图配同一张静态卡。 |
| 结尾 | 一句明确判断或可复制动作；自然结束。 | 每期重复同一句关注口号。 |

新增**人工观看门禁**：手机尺寸、静音看前 5 秒，再开声看全片。评审者需能回答“这是给谁的、能看到什么结果、为什么继续看”。答不出即退回改题或改开头，不进入渲染。抽 0.0、0.3、1、3、5 秒帧，确认首帧的实际亮度、可读字和封面承诺兑现；脚本静态检查只作辅助。

新增**证据门禁**：成片至少有一段来源可追溯的真实产品画面或实际操作结果；使用厂商演示须明确标“官方演示”，使用示意动画须标“示意”。合成图不得冒充实际界面。现有渲染模板可保留作过渡与来源标注，不再占正片大部分时间。

## 4. 标题与封面：同一个承诺

先定观众要做的事和结果，再写**唯一主标题**，最后做封面。每个平台可以按长度调整，但核心承诺、限制和视频内容一致；发布包须记录**最终实际采用的标题**，不能只放三个备选让发布环节临时选。

- 主标题优先用“任务＋结果/限制”。星数、期号、许可证退到脚注，除非视频本身就在分析 GitHub 热度。
- 3:4 封面只放一个主句和一个可识别的真实视觉证据；主句尽量 6–12 个汉字，移动端缩到信息流大小后仍能读。
- 柴主编头像可以做角标或讲述者，不能占去结果画面的主要面积。视觉识别保持，但不要要求每期复制同一套高密度清单。
- GPT 可以做背景和装饰，涉及产品 UI、数值和功能效果时用真实截图或可复算的排版。现有 OCR、尺寸、边距、封面出处门禁继续跑；再加**缩略图人工评审**和**承诺—前 5 秒匹配**。
- 封面好坏只用同平台、同曝光来源的点击数据判断。没有单条 CTR 时标“未知”；不能用逐日总 CTR 或跨期播放量证明某张封面有效。

**EP.216 的改题示例**：原题“最高六千二百星 三个开源工具”拆成“Mac 修图有没有可用的开源选择？”一条。先在符合条件的 Mac 上真实安装并做一张图的修图任务，展示完成结果、操作成本和系统限制；若无法实测，这条降为“官方仓库简报”，暂不以“替代 Photoshop”或“推荐安装”发布。封面具体文案由实测结果决定，不能先写效果再找证据。

## 5. 试行和数据判断

**第一步：固化快照。** 09-28 的逐条数据现已拿到，按“下载时间的累计快照”回填 EP.208–218；不冒充 24/48/72h 时点。导出缺少曝光、单条封面 CTR、流量来源和取关，留作未知。EP.216 的平台竖封面曾被 4:3 中心裁替换，单独标注；视频号未发、小红书待人工提交，不能算“三平台表现”。

**第二步：6–8 条新基线。** 按上面的内容标准制作，一天最多选一条同系列，选题不合格则跳过。统一在固定的发布窗口试行，但不要把“08 点最好”当因果定律。记录制作时长、是否实测、证据秒数、首 5 秒结构、最终标题、封面、实际发布状态。多项内容变化同时发生，因此这批只建立新基线，不声称哪一个改动单独起效。

**第三步：分层比较。** 每条在发布后 24h 和 72h 记录同龄数据，优先看 5s 留存、平均观看时长、收藏与关注/千次播放；同时看曝光和 CTR，区分“没人点”与“点进来就划走”。按平台、题材、发布时间和时长分层，与旧期中位数作方向性对照。样本少时只写“观察到”，不写“证明”。

**第四步：小实验。** 新基线稳定后一次只改一个主要变量，例如“真实结果首帧 vs 结论文字首帧”或“任务标题 vs 仓库热度标题”。有平台原生封面 A/B 功能时才用同内容双封面；不要靠重复投稿做 A/B。

临时观察线：旧五场期 5s 完播中位 32.4% 可作参照，但不是平台标准，也不是单条生死线。连续 6–8 条的中位数若未改善，优先复查选题和实证强度；若 CTR 改善但 5s 不动，复查承诺与首帧兑现；若 5s 改善但完播仍低，缩中段并去掉重复口径。

## 6. 对正式流水线的改动顺序

1. **先改编辑规则**：把 skill 中“默认三件套/固定五场/统一 CTA/星数前置”的强制项改成可选模板，并让准入四问成为生产前硬门。现有 `docs/端到端流程.md` 保留为 09-28 现状快照。
2. **再改素材与成片模板**：支持真实录屏、结果对比和来源角标；模板五场可继续用于确实适合清单的选题。
3. **最后改自动门禁**：增加前 5 秒抽帧、实际标题落包、证据素材出处检查；修复已知 motion 假 PASS、门禁 I 未比包内副本、封面数字参数未落包等问题。
4. **复盘自动化**：先确保后台导出与期号映射准确，再把 24h/72h 实际数字写回，不允许空表被当成“已经复盘”。

同类创作者的实时选题采样与 Jev 接入判断，见 [Jev 与同类创作者选题雷达试采](Jev与同类创作者选题雷达试采-2026-09-28.md)。

这次不需要推倒事实核验、词级字幕、渲染、音视频同步和发布后平台校验；真正要推倒的是“热榜三件套 → 自评 ≥70 → 同模版量产 → 技术门禁 PASS 即质量合格”的编辑假设。
